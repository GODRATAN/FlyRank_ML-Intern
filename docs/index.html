Content Refresh Prioritization from Search Performance Signals

Can a simple machine-learning model help an editor decide which content observations deserve review first?

Warehouse release v20260703 · Content Refresh lane · March 2026 decision window · April 2026 outcome window

At a glance Problem Data Method Results Limits Recommendations Reproducibility Credit

Abstract

This study asks whether a simple machine-learning model can rank content observations for human review using signals available before a future search-performance outcome. It uses the FlyRank internship warehouse release v20260703, with March 2026 search-performance features and an April 2026 outcome defined as a drop of at least 20% in average daily GSC impressions. Logistic Regression turns five March-only features into a ranking score and is compared with a transparent Week-4 baseline using an 80/20 client-grouped holdout. On 22,411 held-out observations across eight clients, the model measured Precision@20 of 0.85 and Precision@50 of 0.82, compared with 0.50 and 0.52 for the baseline. The result is evidence for prioritization and human review in this experiment, not evidence that refreshing a page causes better search performance.

How to read this paper: the model does not tell an editor what to change. It creates an ordered review queue. Humans still inspect the page, context, search intent and business situation before acting.

1. Introduction / Problem

Imagine an editor has thousands of pages and only enough time to inspect a small number today. The useful question is not simply “Which pages are bad?” but “Which observations should be reviewed first?”

This project treats that as a ranking problem. A transparent rule gives us a human-readable baseline; a learned model gives us another way to order the same kind of observations.

1 Observe March Search-performance signals available at the decision moment.
2 Define April outcome Mark observations whose average daily impressions fell by at least 20%.
3 Rank Logistic Regression assigns a score used only to order the review queue.
4 Review A human checks context before deciding whether any action is appropriate.

2. Data

The study uses the FlyRank internship warehouse release v20260703, hosted in the gated FlyRank/internship-warehouse dataset. The main table is fact_content_daily_performance, with grain report date × client × content. The release contains approximately 78.8 million daily-performance rows spanning 2025-01-27 through 2026-06-30.

Feature window · March 2026

Only information available in March is used as a predictive input.

  • march_impressions — search exposure
  • march_clicks — observed clicks
  • march_ctr — click rate
  • march_avg_position — search position context
  • march_days_observed — depth of available evidence

Outcome window · April 2026

April is used to define the outcome only. It is not allowed into the March feature set.

Label = 1 when average daily GSC impressions in April are at least 20% lower than average daily GSC impressions in March.

Eligibility and exclusions

  • At least 100 March GSC impressions.
  • At least 14 GSC-observed days in March.
  • At least 14 GSC-observed days in April.
  • Rows without available GSC data were excluded.
  • gsc_avg_position = 0 was treated as unavailable.
  • Future April outcome fields were excluded from model features.
  • Client and content identifiers were used for grouping, never as predictive features.

The final modeling dataset contains 96,268 eligible client-content observations across 40 clients. The client/content identifiers remain pseudonymized; no client names, private URLs or private search queries appear in the paper.

3. Methodology

Model choice

Logistic Regression was chosen as the first learned model because the question is ranking-oriented and the model produces a probability-like score that is easy to inspect and use for ranking. No claim is made that a more complex model could not behave differently.

What the model sees

All five model inputs come from March 2026. April fields exist only on the outcome side. This separation is the core protection against using future information as a feature.

Baseline

The Week-4 baseline prioritizes observations with at least 100 March impressions and CTR below the average CTR for their March average-position bucket. In the held-out evaluation, that position-specific reference was calculated from training rows only.

Validation design

The main evaluation uses an 80/20 client-grouped holdout with random seed 42. Training contains 32 clients and 73,857 rows; testing contains 8 clients and 22,411 rows. There is zero client overlap.

Why Precision@20 and @50?

If the real workflow is “review the first few recommendations,” overall accuracy is less informative than asking how many of the top-ranked observations actually meet the chosen outcome definition.

Plain-English metric: Precision@20 = the share of the first 20 ranked observations that meet the defined future-decline label. Precision@50 is the same idea for the first 50.

Validation audit

Random row split 0.90 0.84 Rows from the same client can appear in both train and test.

Leakage audit

The final feature set contains only March variables. The audit found no future- or label-derived feature names, and no April outcome fields were used as model inputs. The feature-source audit confirmed March 2026 as the source window for all five inputs.

Read the result against the base rate: the held-out test positive-label rate was 0.6437. This matters because precision numbers are easier to interpret when the underlying prevalence is visible. In this experiment, the model's top-ranked precision was above that prevalence; the baseline's reported Precision@20 and @50 were below it.

Model vs Week-4 baseline on the client-grouped held-out test split.

On this held-out-client split, Logistic Regression measured higher precision than the Week-4 baseline at both cutoffs. The random row split produced 0.90 and 0.84, while the stricter client-grouped split produced 0.85 and 0.82, which is why the grouped result is the main estimate.

5. Limitations & Honest Framing

  • The study uses one March feature window and one April outcome window. Results may differ under other time periods.
  • The 20% impression-drop label is an experimental definition, not a universal definition of “content decay.”
  • The main test contains eight held-out clients. That is stronger than a row-random split for this question, but it is still a small held-out client sample.
  • The training and test positive-label rates differ: 0.4664 versus 0.6437. This indicates a noticeable difference in outcome prevalence between these groups.
  • The five features do not capture every relevant factor, including search intent, SERP features, editorial context, business priorities and recent changes outside the warehouse snapshot.
  • The analysis measures ranking performance. It does not establish that refreshing a page causes better search performance.
  • A high model score is a reason to review, not proof that a particular edit is needed.

6. Ranked Recommendations

1. Review high-risk observations with meaningful exposure

Start with observations that have a higher model score and meaningful March search exposure. The purpose is to use limited reviewer time on observations that the model ranks more highly and that have enough current search activity to make inspection potentially useful.

2. If CTR is weak, inspect the search context before editing

Review the title, snippet, query intent, page/result alignment and SERP context. The model does not tell the reviewer which one of these is the problem.

3. Treat low-evidence high-risk observations cautiously

Sparse or changing data can make a score less stable. These observations are candidates for additional evidence or monitoring rather than automatic changes.

Human-review checklist

  1. Check current page and search context.
  2. Check search intent and CTR context.
  3. Check whether a recent content or site change explains the signal.
  4. Check business, brand, legal and editorial context.
  5. Confirm that the suggested action makes sense before changing anything.

What should never be automated here

  • Automatic publishing or rewriting of page content.
  • Automatic title or metadata changes.
  • Automatic deletion, redirects or de-indexing.
  • Automatic legal, brand or sensitive editorial decisions.
  • Treating a high score as proof that a page needs a specific edit.

Cost / value thinking

The practical constraint is reviewer time, not a claimed monetary ROI. Higher-risk, higher-exposure observations can be inspected earlier, but the actual value of a change depends on the page, business context and the result of human review.

Monitoring and retraining

Track Precision@20 and Precision@50 on a recent reviewed sample, data availability, feature distributions and the rate at which reviewers reject high-priority recommendations. Consider a fresh model audit when recent precision falls materially, feature distributions shift, data coverage changes enough to alter the queue, reviewers repeatedly reject high-priority items for the same reason, or the underlying decision/outcome definition changes.

Important: retraining should only follow a fresh leakage audit, an honest validation split and a new comparison with the frozen baseline.
